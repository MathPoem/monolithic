# Generous Auction: геометрический PAB, спецификация распределения и расчёта

**Generous Auction** — детальная проработка варианта «C-тик» из [08 §3.9](08-pay-as-bid.md): транша раунда  
распределяется по **геометрической кривой от вершины книги**, неразобранный остаток  
перетекает вверх. Документ отвечает на два вопроса: *какое именно правило раздачи* и  
*как оно считается лениво* — так, чтобы клеймы и выходы остались O(1), как в v1

---

## TL;DR

1. **Правило.** Живой тик `i` получает долю транши `q^(−i) / V`, где
  `V = Σ q^(−j)` по всем живым тикам, `q ∈ (0,1]` — затухание на тик. Чем выше тик,
   тем больше доля; в плотной книге доля топа стремится к `(1−q)`. Исчерпанный тик
   выбывает, `V` уменьшается — доли остальных растут, сильнее всего у верхних:
   «остаток переходит на большие тики» происходит сам, отдельного механизма не нужно.
2. **Расчёт.** Вся динамика — и межраундовая, и внутрираундовый «водопад» остатка при
  смерти тика — это движение **одного глобального аккумулятора** `G` с
   кусочно-постоянной скоростью `R/W`. Вклад любого тика на любом интервале:
   `q^(τ−i) · R · ΔG` — читается за O(1) одним fixed-point pow. Внутритиковый учёт v1
   (продуктовый аккумулятор `P`) не меняется вообще.
3. **Цена.** Два новых элемента инженерии: ребейз «мантисса + сдвиг» при смене вершины
  (тот же паттерн, что рескейл `P` в v1) и **очередь смертей тиков** (сортированный
   список с хинтами в стиле CCA). Порядок ключей очереди инвариантен к ребейзу —
   массовых обновлений не бывает.
4. **Ручка** `q` **в v2 — иммутабельная** (задаётся при деплое): её смена требует
  перестройки `V` и всех ключей смертей за O(живых тиков). Редактируемыми остаются
   `{K, R}` через pending-механизм v1.

## 1. Правило распределения



### 1.1 Веса

- Живые тики: `A = { i : остаток валюты тика b_i > 0 }`.
- Вес тика: `w_i = q^(τ − i)`, где `τ = max(A)` — вершина книги. Вес топа равен 1,
каждый тик вниз — умножение на `q`.
- Доля тика в транше раунда: `s_i = w_i / W`, где `W = Σ_{j∈A} w_j`.
- Токены тику за раунд: `a_i = R · s_i`; валюта списывается по цене **его** тика:
`c_i = a_i · p_i` (pay-as-bid сохраняется).
- Внутри тика `c_i` делится pro-rata существующим аккумулятором `P` из v1 (§3.4 в 08).

Два свойства, ради которых выбрана именно геометрия (а не гипербола и не ранги):

- **Сдвиг-инвариантность.** `q^(d+m) / Σ q^(d'+m) = q^d / Σ q^d` — появление новой
вершины выше не меняет относительные доли уже стоящих тиков. Якорные манипуляции
(даст у `maxTick`, чтобы «растянуть» кривую) — но-оп для чужих долей; манипулятор
просто сам становится топом и платит топ-цену. Гипербола `1/(1+d)` этим свойством
не обладает.
- **Факторизуемость.** `w_i = q^τ · q^(−i)` — распадается на глобальную и пер-тиковую
часть. Отсюда весь ленивый расчёт (раздел 3). У гиперболы разложения нет, и клейм
деградирует до O(числа смен вершины за историю).

Расстояние — в **тиках цены**, не в рангах живых тиков: тик на 100 тиков ниже топа
получает `q^100 ≈ 0`, даже если он второй в книге. Это осознанно: кривая и есть
«оффсет от реальной цены» — окно участия задано расстоянием по цене, а не местом в
очереди. (Ранговые веса к тому же неленивы: ранг тика меняется от чужих событий.)

### 1.2 Раунд и водопад остатка

Транша раунда «проливается» по долям `s_i`. Если бюджет какого-то тика кончается на
середине транши — с этой точки **остаток той же транши** льётся по перенормированным
долям выживших (тик выбыл из `A`, `W` уменьшился). Если умирает ещё один — ещё одна
перенормировка, и так далее; итераций не больше, чем смертей. Если умерли все —
несобранный остаток уходит в `unsold` (строгий режим: даже единственный биддер не
получает больше своей доли — это и есть анти-кит гарантия уровня раунда; мягкий режим
«остаток последнему живому» — флаг конфигурации).

Важно: «водопад» — это не отдельный алгоритм, а кусочное движение того же глобального
аккумулятора (см. 3.3), поэтому расчёт остаётся точным и путенезависимым.

### 1.3 Совместимость с v1

Не меняются: раунды `{K, R}` и их pending-редактирование, нейтральность внутри раунда
(сворачиваются только завершённые раунды), внутритиковый pro-rata (`P`, эпохи,
рескейл), клейм/выход в любой момент, стриминг выручки, floor, `validationHook`,
битмап тиков. Меняется только `_consume`: вместо «дренируем верхний тик» — движение
`G` между событиями.

Предельные случаи: `q → 0` — строгий приоритет цены (v1); `q = 1` — поровну между
живыми тиками. Важная рамка для оценки сложности: **v1 — вырожденный случай этой
схемы**. Информационная зависимость одинаковая (состояние тика — функция всего, что
съедено выше; лениво амортизируется, чтение O(1) в обоих), но в v1 два механизма
вырождаются в тривиальные: порядок смертей совпадает с порядком цен — очередь смертей
бесплатно заменяется битмапом, — а частично потреблённым бывает ровно один тик
(маргинальный), поэтому pow-формула чтения вырождается в простые mul/div. Доп.
сложность v2 — это ровно цена невырожденности этих двух механизмов, константная,
не асимптотическая. В сплошной книге доля топа `= (1−q)/(1−q^n) → (1−q)`: `q` **напрямую
задаёт мягкий кап вершины** (q=0.75 → топ ≤ ~25% транши, q=0.9 → ≤ ~10%) — но только
при плотной книге; жёсткий кап при любой книге — оверлей варианта A из 08 §3.9.

## 2. Состояние

Глобально (поверх состояния v1):


| Поле                       | Смысл                                                                              |
| -------------------------- | ---------------------------------------------------------------------------------- |
| `q` (Q96)                  | затухание на тик; иммутабельно в v2                                                |
| `G` (мантисса Q96 + сдвиг) | глобальный аккумулятор потребления, в «единицах текущей вершины»                   |
| `W` (Q96)                  | сумма весов живых тиков в единицах вершины; `W ∈ [1, 1/(1−q))` — всегда ограничена |
| `tau`                      | текущая вершина `τ = max(A)`                                                       |
| `shift`                    | счётчик ребейзов (см. 3.4)                                                         |
| очередь смертей            | ключи `G_death(i)`, отсортированы по возрастанию                                   |


Пер-тик (поверх `{remaining, P, epoch, scale}` из v1):


| Поле  | Смысл                                                         |
| ----- | ------------------------------------------------------------- |
| `G_i` | отметка `G` последнего сеттла тика (со своим индексом сдвига) |




## 3. Ленивый расчёт



### 3.1 Главная формула

Между событиями (смерть тика, новый бид, вывод) множество `A`, вершина `τ` и `W`
постоянны. Скорость дренажа тика — `r_i = R · q^(τ−i) / W` токенов за раунд. Введём
глобальный аккумулятор с приращением `dG = Δn / W` за `Δn` раундов. Тогда на любом
интервале:

```text
токены, съеденные тиком i  = q^(τ−i) · R · ΔG
валюта, снятая с тика i    = p_i · q^(τ−i) · R · ΔG
```

Вся межтиковая динамика свёрнута в одно число `G`; пер-тиковая часть `q^(τ−i)` —
одно возведение в степень (≤ 16 умножений Q96 при `maxTick < 2^16`).

### 3.2 Сеттл тика и двухуровневая ленивость

Тик трогается только своими событиями (бид в него, клейм/вывод из него, его смерть).
При касании — **сеттл**: `c = p_i · q^(τ−i) · R · (G − G_i)`, затем ровно как в v1:
`P ← P·(A−c)/A`, `A ← A−c`, `G_i ← G`. Смерть тика — частный случай (`c = A`,
`epoch++`).

Чтение позиции заявки (view, O(1)): вычислить `c` в памяти → эффективные
`A_eff = A − c`, `P_eff = P·A_eff/A` → дальше формулы v1 (`remaining = amount·P_eff/P_entry`,
`bought = (amount − remaining)/p_i`). Два pow на чтение, хинты и индексер по-прежнему
не нужны.

### 3.3 `_sync`: события и водопад

```text
_sync():
    toSell = эмиссия завершённых раундов (как в v1, с pending {K,R} и клампом supply)
    while toSell > 0 and книга не пуста:
        headKey = min(очередь смертей)             // G, при котором умрёт ближайший тик
        dG_max  = headKey − G                      // сколько G можно пройти без смертей
        dG_need = toSell / (R·W) ... точнее: toSell танков хватает на dG = toSell/(R)·(1/W)?
                  // токены, продаваемые на единицу dG: Σ q^(τ−i)·R = R·W  →  dG_need = toSell/(R·W)
        dG = min(dG_max, dG_need)
        G += dG;  toSell −= R·W·dG;  raised += Σ... // выручка копится агрегатно, см. 3.5
        if dG == dG_max:                            // смерть тика
            pop очереди; сеттл умершего (c = A, epoch++), V-обновление: W −= q^(τ−i_dead)
            if умерла вершина: τ' = новая вершина; ребейз (3.4)
    if toSell > 0: unsold += toSell                 // строгий режим
```

Смерть на середине транши раунда обрабатывается этим же циклом автоматически — `dG`
просто разбивается на куски с разными `W`. Каждый тик умирает один раз за жизнь →
амортизация как в v1. Кэп итераций + резюмируемость через `carry` (в т.ч. финализация
в несколько транзакций) — как в v1. Заметьте: **число итераций цикла идентично v1** —
по одной на умирающий тик (в v1 «пройти сквозь тик» и есть его смерть); дельта только
в константе тела итерации (~×2: pop очереди + апдейт `W`/`W_p` + изредка ребейз против
clear-бита + next-lookup). Бессобытийные отрезки в обоих сворачиваются в один шаг без
итераций.

### 3.4 Ребейз: мантисса + сдвиг

`G`, `W` и ключи смертей ведутся «в единицах вершины `τ`». При смене вершины на `τ'`
все они умножаются на `q^(τ−τ')`: вершина опустилась — величины сжимаются (безопасно),
поднялась — растут. Чтобы не переполниться, применяется тот же приём, что у рескейла
`P` в v1: хранится мантисса и глобальный счётчик сдвигов `shift`; при выходе мантиссы
за порог (напр. `2^96`) она делится на `q^64`, `shift++`. Пер-тиковые отметки `G_i` и
ключи очереди хранят индекс сдвига на момент записи; чтение приводит к общему индексу
одним pow.

Ключевое следствие для очереди смертей: при ребейзе **все ключи умножаются на один и
тот же множитель — их порядок не меняется**. Массовых обновлений очереди не бывает;
ребейз — O(1).

### 3.5 Выручка и sold агрегатно

За кусок `dG` продано токенов `R·W·dG` — по определению `W`. Снято валюты
`Σ p_i·q^(τ−i)·R·dG` — нужна вторая агрегатная сумма `W_p = Σ p_i·q^(τ−i)` по живым
тикам, поддерживаемая теми же O(1)-обновлениями при смертях/бидах/выводах, что и `W`.
Тогда `raised += R·W_p·dG`, `sold += R·W·dG` — без обхода тиков.

### 3.6 Очередь смертей

Тик `i` умирает, когда `p_i·q^(τ−i)·R·(G − G_i) = b_i`, т.е. при

```text
G_death(i) = G_i + b_i / (p_i · q^(τ−i) · R)
```

Ключ статичен, пока не меняется бюджет тика; пересчитывается только при биде в тик /
выводе из тика (после сеттла). Структура — отсортированный связный список с хинтом
вставки (паттерн тиков CCA): вставка O(1) с хорошим хинтом, извлечение минимума —
с головы. Богатый низкий тик переживает бедный высокий — порядок смертей не совпадает
с порядком цен, поэтому очередь обязательна (v1 обходился битмапом, потому что там
умирал всегда строго верхний).

## 4. Операции


| Операция              | Что делает поверх v1                                                                                        | Сложность                     |
| --------------------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `bid(tick, amount)`   | `_sync` → сеттл тика → `A += amount` → пересчёт ключа смерти (вставка с хинтом) → если тик выше `τ`: ребейз | O(1)*                         |
| `claim(bidId)`        | `_sync` → чтение через эффективные `A_eff, P_eff` (3.2)                                                     | O(1)                          |
| `withdraw(bidId)`     | `_sync` → сеттл тика → выплаты v1 → пересчёт/удаление ключа; если тик умер и был вершиной — ребейз          | O(1)*                         |
| `sync(maxEvents)`     | движение `G` по 3.3                                                                                         | O(смертей с прошлого касания) |
| `setRoundParams(K,R)` | как в v1 (pending с границы раунда); смена `R` меняет скорость `G`, но не формулы                           | O(1)                          |
| `set q`               | **нет в v2**: требует перестройки `W`, `W_p` и всех ключей — O(живых тиков)                                 | —                             |


 плюс вставка в очередь: O(1) с хинтом, O(n) худший без.

Газ (оценка): бид/вывод ≈ v1 + 15–25k (два pow, сеттл, ключ); чтение позиции ≈ v1 +
~5k (pow); смерть тика в sync ≈ ~15k. Простой тик не стоит ничего, пока его не трогают.

## 5. Числовой пример

`δ = 5%`, floor = 1 USDG; живые тики: `2 (p=1.1025)`, `1 (p=1.05)`, `0 (p=1.0)`.
Бюджеты: `b₂ = 100`, `b₁ = 210`, `b₀ = 500` USDG. `q = 0.5`, `R = 70` токенов/раунд.

Веса от вершины `τ=2`: `w₂=1, w₁=0.5, w₀=0.25`; `W = 1.75`. Доли: `4/7, 2/7, 1/7` →
за раунд: 40, 20, 10 токенов (валютой: 44.1, 21.0, 10.0).

**Раунды 1–2 (сегмент без событий).** `ΔG = 2/1.75 = 1.1429`. Съедено: тик 2 — 80 ток
(88.2 USDG, остаток 11.8), тик 1 — 40 (42.0), тик 0 — 20 (20.0).

**Раунд 3 — смерть тика 2.** Ключ смерти тика 2: `G_death = 100/(1.1025·1·70) = 1.296`;
до него `dG = 0.1529` (это 26.76% транши). На этом куске: тик 2 добирает 10.70 ток
(11.8 USDG — бюджет исчерпан, `epoch++`), тик 1 — 5.35, тик 0 — 2.68. Вершина теперь
`τ' = 1` — ребейз: `G, W`, ключи × `q^(2−1) = 0.5`; новые веса `w₁=1, w₀=0.5`,
`W = 1.5`, доли `2/3` и `1/3`. Остаток транши (51.27 ток) льётся по новым долям:
тик 1 — 34.18 (35.89 USDG), тик 0 — 17.09. Вот «неразобранная эмиссия перешла на
большие тики»: доля тика 1 подскочила с 2/7 до 2/3.

**Раунд 4.** Тик 1 — 46.67 ток (49.0 USDG), тик 0 — 23.33.

Итог за 4 раунда (280 токенов эмиссии):


| Тик | Потрачено USDG      | Куплено токенов | Проверка               |
| --- | ------------------- | --------------- | ---------------------- |
| 2   | 100.0 (весь бюджет) | 90.70           | `100/1.1025 = 90.70` ✓ |
| 1   | 132.51              | 126.20          | остаток бюджета 77.49  |
| 0   | 63.10               | 63.10           | цена 1.0               |
| Σ   | 295.61              | **280.00**      | `= 4·R` ✓              |


Сквозная проверка формулы одним аккумулятором: `G` по кускам
`1.1429 + 0.1529 → ×0.5 (ребейз) → 0.6479 + 0.4883 + 0.6667 = 1.8028`; тик 0:
`q^(τ−0)·R·G = 0.5·70·1.8028 = 63.10` ✓ — сошлось с посчитанным по раундам.

## 6. Свойства и границы

- **Клиринговой цены нет — вдвойне.** Как во всяком pay-as-bid, нет единой цены платежа
(каждый платит цену своего тика, продажи финальны); а в геометрическом варианте
растворяется и резкая маргинальная граница v1 — вместо отсечки «попал/не попал»
плавный градиент участия. Референс, где он нужен (сид пула v4, оракулы): вершина
книги `topTick` или VWAP продаж `raised/sold`.
- **Широта**: каждый живой тик получает свою долю каждый раунд; окно фактического
участия ≈ `log_q(пыль)` тиков вниз от вершины (при q=0.9 — десятки тиков).
- **Анти-кит**: мягкий кап вершины `≈ (1−q)` в плотной книге; в строгом unsold-режиме
одиночка на пустой книге тоже ограничен своей долей. Жёсткая гарантия при любой
книге — только с кап-оверлеем (08 §3.9-A).
- **Обходы**: фрагментация по k тикам собирает k весов (трение `minBid × k` + худшие
позиции ниже) — лечится вогнутым бюджет-весом или капом; мультиадрес — только
`validationHook`. Якорные игры мертвы по сдвиг-инвариантности.

| Внутри тика pro-rata                          | алгоритмы аллокации CME на ценовом уровне; budget pacing рекламных аукционов (пропорционально с бюджетами-капами, Fisher markets)                                                                                                                                                                                                                                                                                                                         |


Сводно: механизм = «WFQ поверх ценовой лестницы» с pay-as-bid-оплатой; новизна — в
комбинации, компоненты — заимствованно-проверенные. Примечательное отличие от бирж:
классический матчинг никогда не делит объём **между** ценовыми уровнями — мы делаем
это сознательно ради оффсета распределения.

Крипто-родственники по пределам ручки `q` (целиком механизм в крипте не встречен —
см. также обзор в 08 §2):

- **q = 1, «overflow sales»**: PancakeSwap IFO (overflow method), Mango-style IDO
vaults — pro-rata из общего котла с рефандом излишка; **StreamSwap** (Cosmos) —
стриминговая версия того же, без ценового измерения;
- **q → 0**: CCA / EasyAuction / Axis EMP — строгий клиринг по лестнице; их pro-rata
на маргинальной цене = наш внутритиковый слой;
- **веса с ренормализацией, но не от цены**: Curve gauge weights (эмиссия ∝ голосам),
Astroport Lockdrop (веса от длины лока);
- **аккумуляторная бухгалтерия**: MasterChef / индексы Aave / funding перпов — G-паттерн.

Ниша и риск одновременно: «pro-rata по весам поперёк ценовых уровней» не делает никто —
экономика не обкатана чужим продом, отсюда приоритет симуляций (§7).

## Приложение A — полный вывод формул

Сквозной вывод расчёта одного розыгрыша (для стриминга всё то же с `T` = кумулятивная
эмиссия). Числовая проверка — на демо-сценарии из плейграунда (`?demo`).

### A.1 Обозначения

Цена `p(i) = floor·(1+δ)^i`; бюджет тика `B_i` (валюта); ёмкость `cap_i = B_i/p_i`
(токены); розыгрыш `R`; живое множество `A`, вершина `τ = max A`; `T` — налито токенов.

### A.2 Мгновенное правило

`w_i = q^(τ−i)`, `W = Σ w_j`, доля `s_i = w_i/W`; налив `dT` даёт тику `s_i·dT` токенов
(`p_i·s_i·dT` валюты).

### A.3 Шифт-инвариантность

`s_i = q^(−i)/V`, где `V = Σ_{j∈A} q^(−j)` — τ в долях сокращается; нужен только для
ограниченной арифметики ончейн (A.8).

### A.4 Факторизация и накопитель

`da_i/dT = q^(−i)/V` → вводим `dC = dT/V`, получаем `da_i = q^(−i)·dC` и, интегрируя
по кускам постоянного `V`:

```text
a_i = q^(−i)·(C − C_вход_i)                                   (★)
```

Один скаляр `C` описывает всех живых; профиль по тикам всегда `∝ q^(−i)` — отсюда
гладкая огибающая и O(1)-чтения.

### A.5 Пороги смерти

Из `a_i = cap_i`: `κ_i = cap_i·q^i = B_i·q^i/p_i` — статичный ключ; порядок смертей =
возрастание `κ` (не порядок цен!).

### A.6 Алгоритм за линейное время

На стадии `ΔT = V·ΔC` →

```text
V = Σ q^(−i); C = 0; осталось = R
для тиков по возрастанию κ:
    ΔT = V·(κ_i − C)
    если ΔT > осталось: C += осталось/V; конец
    C = κ_i; осталось −= ΔT; V −= q^(−i)      # смерть, итог = cap_i
живые: a_i = q^(−i)·C
```

Сортировка `O(n log n)` + проход `O(n)`; ончейн сортировка размазана в очередь смертей.

### A.7 Сохранение, выручка, pro-rata

`Σ_i q^(−i)dC = V·dC = dT` ⇒ `Σ a_i + unsold = R`; `raised = Σ p_i·a_i` (pay-as-bid).
Внутри тика: доля потраченного `f_i = p_i·a_i/B_i` одна на всех его ставках;
`spent = β·f_i`, `bought = β·f_i/p_i`; входы посреди жизни — продуктовый `P` из v1.

### A.8 Ончейн-форма (ребейз)

В «единицах вершины»: `ŵ_i = q^(τ−i) ∈ (0,1]`, `Ŵ = q^τ·V ∈ [1, 1/(1−q))`,
`dĜ = dT/(R·Ŵ)`, `a_i = R·q^(τ−i)·(Ĝ − Ĝ_вход_i)`; связь `C = R·q^τ·Ĝ`. Смена вершины
умножает всё на общий `q^(τ−τ′)` — порядок ключей очереди сохраняется; границы чисел —
мантисса+шифт. Порог: `Ĝ_смерти(i) = Ĝ_вход_i + B_i/(R·p_i·q^(τ−i))`. Огибающая
графика: `E(x) = R·Ĝ·q^(τ−x)`.

### A.9 Проверка на демо

`q=0.5, R=150`; `q^(−i)` = 8/4/2/1, `V=15`; `κ`: тик3=2.5, тик1=5, тик2=50, тик0=100.
Проход: ΔT=37.5 (†3) → ΔT=17.5 (†1) → остаток 95, `C = 5+95/5 = 24`. Итоги: 20/96/10/24,
Σ=150; выжившие `96/24 = q^(−2)` — на огибающей.
